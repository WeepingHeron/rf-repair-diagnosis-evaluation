# RF 회로 복구 프로젝트 점검 및 제출 전 확장 검토

점검일: 2026-09-06 KST. 대상 코드: `0248ddf`. 기존 코드·실험 로그·제출 DOCX는 수정하지 않았다. 이번 점검은 로컬 테스트, 저장된 데이터의 독립 재집계, 실제 ngspice 재실행, 원고 내용 및 렌더 확인, 관련 문헌의 제한적 추가 검색으로 수행했다. 새 LLM API 호출은 하지 않았다.

현재 프로젝트는 **하나의 이상적 RF 필터에서 제한된 수정과 외부 검증을 실행하는 연구 프로토타입**으로는 근거가 갖춰져 있다. 주요 복구 수치도 재현됐다. 제출 전 우선순위는 단위·측정 검증 결함 수정, 최신 결과를 만드는 경로 정리, 구조 고장의 쉬운 진단 단서 명시, 동일 예산 대조군 보강이다. 새로운 모델이나 RAG보다 이 네 가지가 현재 논문의 설득력에 직접 기여한다.

장점은 성공 판정을 LLM에 맡기지 않는 구조, 허용 연산의 제한, 진단과 기능 복구의 분리, 개발 실험과 holdout을 분리한 기록, 부정적 결과의 보존이다. 특히 원인을 다르게 지목하고도 다른 부품 조정으로 복구한 3건과, 진단이 맞아도 수치가 1000배 틀려 실패한 사례는 논문의 설명력이 높은 관찰이다.

## 개선 우선순위

### 1. 단위 변환기가 수치 의미와 차원을 보존하지 않는 입력이 있다

근거: `src/rf_repair/netlist.py:13`의 정규식과 `normalize_spice_quantity`.

실제 재현 결과는 다음과 같다.

```text
normalize_spice_quantity("1 F", expected_unit="F") -> "1f"
normalize_spice_quantity("0.000000000003183 F", expected_unit="F") -> "0.000000000003183f"
normalize_spice_quantity("1 F", expected_unit="H") -> "1f"
```

대소문자를 무시하는 정규식이 단위 F를 접두사 femto로 먼저 소비한다. 첫 두 사례는 수치를 10^-15배로 바꾸고, 세 번째는 잘못된 차원을 통과시킨다. 이는 문서의 “숫자 의미를 바꾸지 않는 변환”이라는 계약과 충돌한다.

명시적 물리 단위와 SPICE 접두사 표기를 구분해 파싱하고, SI 값으로 변환한 뒤 차원·유한성·양수 여부를 검사하는 방식이 적절하다. 명시적 `F`, `H`, `pF`, 지수 표기, 공백, 잘못된 차원에 대한 회귀 검사를 추가해야 한다. 파서가 숨겨진 정상값에 맞춰 오류를 자동 교정해서는 안 된다.

이번에 점검한 normalized 구조 실험의 저장 제안에서는 이 무접두사 F 형태가 발견되지 않았다. 기존 회로의 PASS/FAIL도 모두 재현되어, 현재 결과 수치가 틀렸다는 증거는 없다. 그래도 확장 실험 전에 수정해야 하는 구현 결함이다.

별도로 `src/rf_repair/agent.py:36`의 `_SPICE_VALUE`와 `apply_restricted_patch`는 `0`, `1e999`, `1e-999`도 수용했다. 현재는 숫자 모양을 검사할 뿐 양수·유한성·실행 가능한 범위를 검사하지 않는다. 시뮬레이터가 최종 실패로 막는 것과 patch 정책이 올바른 것은 별개다. 숨겨진 정답값을 쓰지 않는 부품별 사전 허용 범위를 정하고, 0·overflow·underflow를 simulation 이전에 거절해야 한다.

### 2. 측정 데이터가 충분한지 확인하지 않고 PASS를 낼 수 있다

근거: `src/rf_repair/simulator.py:49`의 `_nearest`, `_measure` 및 `src/rf_repair/validator.py`.

70, 100, 140 MHz의 3점만 주고 S21을 각각 -30, 0, -30 dB, S11을 -40 dB로 설정하면 현재 검증기는 PASS를 반환한다. 실제로 측정하지 않은 95·105 MHz의 통과대역 조건에 모두 100 MHz 값을 재사용하기 때문이다.

주파수 배열의 유한성·엄격한 증가·중복·범위·필수 측정점과의 최대 오차를 검증해야 한다. 고정된 현재 실험은 1501점 sweep 계약까지 검사할 수 있다. 향후 adaptive sweep을 사용한다면 점 개수를 강제하는 대신 각 필수 주파수의 확보와 보간 오차 기준을 정의해야 한다. 데이터 파싱 실패는 patch 거절과 구분해 기록하는 것이 좋다.

기존 7개 실험에서 검사한 원시 표 184개는 모두 50~200 MHz, 1501점이고 요구한 5개 주파수가 정확하게 존재했다. 따라서 이번 반례는 기존 실험의 측정 누락을 발견한 것이 아니라, 검증기의 방어가 부족함을 보여준다.

### 3. Blind 구조 고장의 진단이 텍스트 규칙만으로 풀린다

근거: `src/rf_repair/agent.py`의 고정된 부품 enum과 structural prompt, `faults/blind/`, `faults/holdout/bpf_structural_blind_holdout_v3.json` 및 저장된 `faulty.cir`.

`RFAULT1`은 원래 부품명을 직접 포함하지 않지만 다음 단서가 남아 있다.

- 정상 후보가 C1~C3, L1~L3로 고정되어 있어 netlist에서 빠진 이름을 찾으면 원래 부품을 알 수 있다.
- 1T/1m 저항값과 특수 표식은 open/short 위치와 유형을 쉽게 알려준다.
- 포트 이름과 50 Ω 목표값이 있어 변경된 포트의 이름과 z0만으로 source/load 분류가 가능하다.
- 회로 제목·주석에 Butterworth, 차수, f0, FBW, prototype g 값도 제공된다.

이번 점검에서 모델이나 SPICE 측정 없이 공개된 후보 목록, netlist 이름·값, 목표 임피던스만 읽는 규칙을 구성했다. 개발 6개와 holdout 6개에서 위치 및 유형을 **각각 6/6**, 합계 **12/12** 맞혔다. 정답 manifest는 예측 후 점수 확인에만 사용했다. 이는 진단 결과이며 복구값 선택 또는 성능 회복까지 검증한 규칙 기준선은 아니다.

따라서 현재의 100% 위치 진단을 일반적인 RF 원인 추론 능력으로 해석하면 안 된다. 논문에서는 “정상 부품명 직접 표식을 제거한 제한적 blind 설정”으로 범위를 좁히고, 이 규칙 기준선을 추가하는 것이 우선이다. 이름만 무작위화해도 후보 목록의 결손이나 유일한 고장 표식이 남으면 문제가 해소되지 않는다.

확장 평가에서는 이름·줄 순서·불필요한 설계 주석을 바꾸고, 동적으로 생성한 스키마가 정답 부품 목록을 노출하지 않게 해야 한다. 구조 고장은 ‘위치 단서가 제공된 복원 과제’로 별도 보고할 수도 있다. 더 현실적인 진단 연구로 가려면 고장 netlist를 완전히 관측한다는 가정 자체를 재검토해야 한다.

### 4. 현재 표 생성 스크립트는 최신 논문을 재현하지 않는다

근거: `scripts/build_paper_table_data.py:24`와 `build/paper_table_data.json`.

스크립트는 여전히 부품명이 드러나는 이전 structural v1.0과 normalized v1.1을 읽는다. 생성 데이터에는 이전 구조 진단 15/18과 normalized 합계 복구 48/48이 남아 있다. 최신 논문은 Blind strict 진단 10/18과 합계 복구 46/48을 사용한다.

제출 DOCX의 숫자는 이번 재검산 결과와 일치한다. 문제는 저장소의 “논문 표 생성” 경로를 다시 실행하면 최신 논문의 근거를 재현할 수 없다는 점이다. 최신 7개 프로토콜을 지정한 단일 결과 계약을 만들고 JSON, Markdown, 원고 표가 같은 집계에서 나오게 해야 한다. `paper/primary_results_audit.ipynb`가 최신 실험 선택을 이미 담고 있으므로 이를 기준으로 정리할 수 있다. README의 초기 현재 상태와 specification의 DRAFT 표기도 실험별 동결 상태와 구분해 갱신할 필요가 있다.

### 5. 피드백 효과와 추가 시도 효과를 분리해야 한다

현재 one-shot은 1회, 폐루프는 최대 3회의 호출을 사용한다. 값 고장에서 26/30→30/30의 추가 복구가 발생했지만, 추가 시도만으로도 얻을 수 있는 개선인지 분리하지 못했다. 제출 원고가 이미 인과 효과를 단정하지 않는 점은 적절하다.

권장 대조는 같은 모델·출력 상한·초기 증거·수정 정책·최대 3회 예산에서, (A) 이전 후보의 결과를 받지 않는 재시도와 (B) 이전 실패 및 SPICE 결과를 받는 재시도를 비교하는 것이다. 두 조건 모두 evaluator가 각 후보를 검증하고 성공 시 종료하며, 성공 판정 외의 피드백이 A에 전달되지 않게 한다. 각 조건의 success@1, success@3, 실제 호출 수, 후보 simulation 수, 토큰을 보고하면 된다.

현 deterministic grid는 고장 배율의 역수 후보를 사용하고 65회 simulation을 소비했다. 그대로도 oracle-informed 기준선으로는 유용하지만 동등한 예산의 우열 근거는 아니다. 별도의 3후보 budget 결과와, 알려진 설계 정보만 사용하는 analytic/sensitivity 기준선을 고려할 수 있다.

### 6. 실행 재개와 비용·출처 기록을 강화해야 한다

근거: 두 closed-loop runner의 `final_path.exists()` 재사용 처리와 최초 faulty simulation 실행 순서.

재개 시 manifest hash는 검사하지만 저장된 결과가 같은 spec·prompt 본문·parser·validator·netlist로 만들어졌는지 강제하지 않는다. 구조 실험의 run environment에 protocol hash를 기록해도 재개 시 이전 값과 비교하지 않는다. 완료된 trajectory를 건너뛰기 전에 초기 고장 simulation을 다시 실행하며, summary는 초기 simulation을 fault 수로 추정하므로 실제 재실행 횟수와 달라질 수 있다. 중간 iteration만 저장된 상태에서 재개하면 이전 호출을 다시 수행해 비용 추적이 더 어려워진다.

실행 ID와 입력 계약 hash를 묶고, iteration별 호출·실패·원문·수정 대상·runtime을 append-only 형태로 남기는 것이 좋다. 값 고장 runner에도 구조 runner 수준의 원문과 response ID 기록을 적용해야 한다. 정상값을 사용하지 않는 정규화 patch fingerprint로 동일한 실패 수정안의 반복도 감지할 수 있다. 단, 동작 변경은 새 protocol에만 적용하고 기존 결과를 덮어쓰지 않는다.

현재 기록의 `ngspice_version`은 출력 첫 줄인 `******`인 사례가 있어 실제 버전 증거가 되지 않는다. 의미 있는 버전 행과 실행 파일 정보로 기록해야 한다. `build/`와 `work/`가 Git에서 제외되어 있으므로, 재현 패키지에는 원시 결과와 checksum을 별도로 보존해야 한다. 현재 로컬 원시 실험 디렉터리는 약 59 MB다. 논문·제출 파일도 현재 untracked 상태이나 원격 백업 여부까지 점검하지는 않았다.

### 7. 통계적 해석과 물리적 판정 범위를 더 선명하게 해야 한다

조건당 18회는 서로 다른 고장 18개가 아니라 **6개 고장 × 3회 반복**이다. holdout의 복구 증가 3건은 L1 open의 2건과 L2 short의 1건에 집중됐다. 반복을 모두 독립 고장 표본처럼 처리하지 말고 fault별 결과와 반복 변동을 보고해야 한다. 새 회로·새 고장 사례를 늘리는 편이 같은 여섯 사례의 반복만 늘리는 것보다 일반화 검토에 유리하다. 통계 검정을 추가한다면 fault 단위를 고려한 설계가 필요하고, 여섯 cluster만으로 강한 유의성 결론을 내리지 않는 것이 적절하다.

현재 validator의 PASS는 고정한 7개 수치 제약의 통과를 뜻한다. 측정 지점 사이 전체 통과대역의 ripple, 대역폭, 출력 반사 S22, 넓은 저지대역의 최악값까지 보장하지 않는다. 우선 기존 전체 주파수 표를 추가 분석해 보상 복구가 어떤 응답 변화를 남기는지 보여줄 수 있다. 새 제약을 넣으면 기존 성공률의 정의가 달라지므로 별도 specification 버전과 보조 평가로 보고해야 한다.

포트 z0 수정은 ngspice RF port 자체의 직렬 내부 임피던스와 관련된다. 향후 matching-network 실험에서는 고정된 측정 기준과 수정 가능한 실제 source/load 소자를 분리해, 측정 조건 수정과 회로 복구의 경계를 명시하는 것이 좋다. [ngspice 공식 매뉴얼의 RF Port 설명](https://ngspice.sourceforge.io/docs/ngspice-43-manual.pdf).

### 8. 원고 내용은 근거와 맞지만 최종 렌더 확인은 남아 있다

제출 DOCX에서 주 수치와 한계 설명을 직접 읽어 대조했다. OOXML에는 표 4개가 있으며 이 중 하나는 상단 레이아웃 표이고 결과표는 3개다. 추적 변경은 0건이었다.

현재 환경에서 원본 DOCX를 다시 렌더하면 2쪽이 생성되지만 한글 글리프가 대량 누락된다. 원문 XML에는 한글이 있으며, 제출 패키지 README도 이 자동 변환 문제를 기록하고 있다. 따라서 이를 곧바로 원본 손상으로 단정하지 않으며, 이번 자동 렌더만으로 한글 조판이 정상이라고도 판정하지 않는다. 최종 원고가 확정된 뒤 Word 또는 실제 제출 미리보기에서 2~3쪽, 한글, 그림, 표를 확인해야 한다. 이번 점검에서는 원본 글꼴이나 레이아웃을 변경하지 않았다.

## 연구 확장 선택

| 확장 | 연구상 얻는 근거 | 예상 작업량 | 권고 |
|---|---|---|---|
| 파서·validator 보강과 최신 결과 재생성 | 기존 결과를 유지하면서 실행·재현 신뢰도 개선 | 1~2일 | 제출 전 필수 |
| 같은 최대 호출 예산의 no-feedback 대조군 | 추가 시도와 피드백의 차이 분리 | 2~3일 | 가장 우선하는 추가 실험 |
| 새 설계 파라미터·이름·순서의 미관측 값 고장 | 고정 값과 표현 단서에 대한 의존성 확인 | 2~3일 | 대조군과 함께 권장 |
| L형 matching network 한 종류 | 다른 topology로의 제한적 전이 | 3~5일 | 앞선 작업이 끝날 때 선택 |
| 결정적 수치 계산 도구 추가 | 차원·지수 오류를 줄이는 방법 검토 | 2~3일 | 범위를 작게 잡은 대안 |
| ESR·Q·부품 편차와 Monte Carlo | 이상소자 가정 아래 숨은 민감도 확인 | 4~7일 이상 | 제출 후 우선 확장 |
| RAG 또는 추가 모델 비교 | 지식 주입·모델 의존성 검토 | corpus와 평가 계약에 따라 달라짐 | 현 제출에서는 후순위 |
| LNA·복합 고장·실측 | 능동 회로와 현실 환경까지 확장 | 수주 이상 | 후속 연구로 분리 |

작업량은 현재 구조를 검토한 계획 추정이며 보장된 소요 시간이 아니다. 표의 모든 작업을 10일 안에 수행하자는 의미도 아니다.

추천안은 필수 수정 뒤 **새로운 값 고장 설계 + 동일 예산 두 조건**에 집중하는 것이다. 예를 들어 사전에 확정한 12개 미사용 사례 × 3회 반복 × 2조건이면 72 trajectory, 조건별 최대 3회일 때 LLM 호출 상한은 216회다. 이는 실행 제안이며 이번 점검에서 수행하지 않았다. 모델 가격을 새로 조회하지 않았으므로 금액은 추정하지 않았다. 사례는 먼저 정상 PASS·고장 FAIL·허용된 oracle 복구 PASS를 확인하고, 선별 이유와 탈락 사례를 기록한 후 모델 실행 전에 고정해야 한다.

matching network를 추가하려면 기존 BPF의 95·100·105 MHz 제약을 그대로 재사용하면 안 된다. 회로별 spec, 측정 주파수, 수정 가능 요소, 정상/고장 생성기와 validator를 분리해야 한다. 현재 `C1~C3/L1~L3` enum과 100 MHz prompt, runner의 고정 경로가 공통 실행기를 막고 있으므로 `CircuitDefinition`에 해당 정보를 모으는 작은 리팩터링부터 필요하다. 새 topology에서 한 번 성공한 결과는 일반화 증명이 아닌 전이 파일럿으로 보고한다.

## 선행연구와 차별화

이번 검색은 기존 참고문헌과 가까운 신규 문헌의 제한적 확인이며, 체계적 문헌고찰이나 신규성 보증은 아니다.

[WiseEDA](https://www.sciencedirect.com/science/article/pii/S1879239125000566)는 RF 필터 파라미터 최적화를 다루고, [NetlistBench](https://arxiv.org/abs/2608.12197)는 SPICE netlist 인식·조작을 결정적인 구조 기준으로 평가한다. 따라서 “LLM에 SPICE를 연결하고 외부 검증한다”만으로 연구의 새로움을 주장하기는 어렵다.

추가로 확인한 [Constraint-aware specialized large language models for RF circuit reasoning](https://www.sciencedirect.com/science/article/pii/S1879239126003607)은 RF-LLM, RF 도메인 적응, 제약을 활용한 검색·문맥 보강, 수치 및 netlist 분석을 다룬다. 현재 참고문헌 검증 문서에는 이 연구가 없다. 출판사에서 확인 가능한 초록과 본문 발췌 범위에서 RF 지식 보강이라는 확장 방향과 겹치므로, RAG 추가 자체를 차별점으로 내세우기 전에 비교해야 한다. 이 점검에서 해당 논문의 전체 실험을 재현하거나 모든 세부사항을 확인하지는 않았다.

현재 프로젝트의 더 구체적인 기여 후보는 **합성 RF 고장의 원인 진단과 기능 복구를 분리하고, 단위·유형 인터페이스 실패와 실제 수치 추론 실패를 구분해 외부 시뮬레이터로 평가하는 절차**다. 동일 예산 대조와 덜 단서 의존적인 사례를 추가하면 이 기여를 더 설득력 있게 설명할 수 있다. SPICED+ 등 기존 교정 연구와는 보안 위협, 성능 고장, 입력 정보, 허용 수정, 성공 지표를 항목별로 비교해야 한다.

- **9/6~9/7:** 단위·측정·허용값 결함 보강, 현재 결과를 재생성하는 경로 정리, 원시 데이터 보존. 기존 수치가 달라지면 원인을 먼저 설명하고 추가 실험을 미룬다.

- **9/11~9/12:** 실패 원인과 fault별 변동을 분석한다. 이때까지 matching network의 정상/고장/oracle 검증이 끝나지 않으면 해당 확장은 제출 후로 넘긴다.
- **9/13:** 실험·집계·주장을 동결하고 원고를 갱신한다. 개선이 없거나 악화된 결과도 보존한다.

- **9/16:** 접수와 최종 확인을 위한 여유로 남긴다.

최소 완성안은 버그 수정·결과 재현 경로 정리·blind 한계 명시다. 권장 완성안은 여기에 새 사례와 동일 예산 대조군을 추가하는 것이다. 다른 topology, RAG, 능동 회로를 동시에 넣는 것은 이번 마감의 우선순위에 맞지 않는다.
